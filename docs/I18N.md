# Internationalisation (i18n)

Languages: **az (default), tr, en, ru**. All four are fully supported on web, admin, mobile, emails, notifications and AI output.
Russian stays (final product decision). Campus content is never auto-translated; names (universities, courses, people) are never translated.

Status: `packages/i18n` and the web wiring are **implemented and tested** (vitest). The Supabase email wiring and the
`locale_set_at` migration against a hosted project are **not verified** (see "Not verified").

## Package: `@unimate/i18n`

| Import | Contents | Depends on |
| - | - | - |
| `@unimate/i18n` | catalogs, `t`, formatting, collation, `resolveLocale` / `reconcileLocale`, `renderNotification` | `@unimate/core` only. No React, no DOM |
| `@unimate/i18n/react` | `I18nProvider`, `useI18n`, `useT`, `useLocale` | React (peer) |

Key API (all take the locale as the first argument, so they work on a server, in an edge function or in a component):

```ts
import { t, formatDate, formatCurrency, sortStrings, LOCALES, DEFAULT_LOCALE } from "@unimate/i18n";
t("ru", "usage.maxPages", { n: 3 });          // "До 3 страниц на документ"  (typed key paths: MessageKey)
formatDate("az", d, { dateStyle: "long", timeZone: "Asia/Baku" });
formatCurrency("az", 12.5);                    // AZN by default: "12,50 ₼"
sortStrings("az", names);                      // ə after e, ı before i, ç ş ğ ö ü in place
```

Message syntax (ICU-lite): `{name}`, `{n, plural, =0 {none} one {# card} other {# cards}}` (`#` = locale-formatted number),
`{g, select, f {...} other {...}}`. Plural categories come from `Intl.PluralRules`: az/tr/en use `one|other`, ru uses
`one|few|many|other`. Every plural needs `other`. Missing arguments stay as written. Missing keys fall back to az, then to the key.

Formatting: `formatNumber`, `formatPercent` (fraction in), `formatCurrency` (AZN default), `formatDate`, `formatTime`,
`formatDateTime`, `formatRelativeTime(locale, date, now?)`, `formatBytes`, `formatList`. They are plain `Intl` calls with tags
`az-Latn-AZ`, `tr-TR`, `en-GB`, `ru-RU`. Always pass `timeZone` in tests. Hermes (React Native) needs Intl with these locales.

## Using it

### Web (`apps/web`)
- Server components: `const { t, locale } = await getT()` from `@/i18n/server` (reads the `um-locale` cookie).
- Client components: `const { t, locale, date, number } = useI18n()` from `@unimate/i18n/react`.
- The root layout renders `<I18nProvider locale>`; `<LocaleSync>` (`apps/web/src/i18n/LocaleSync.tsx`) is mounted in the `(app)` layout and onboarding.
- Changing language: always call `persistLocale(next, userId | null)` (`apps/web/src/i18n/client.ts`). It writes the cookie and
  `<html lang>` first (UI updates at once via `router.refresh()`), then `profiles.locale` and `auth` user metadata `locale`.
  The selectors in settings and onboarding both do this; do not write the cookie yourself.
- Metadata uses `generateMetadata` + `t("meta.description")`.
- Legal pages: `apps/web/src/content/legal/{az,en,ru,tr}.ts`, typed as `Record<Locale, Record<LegalSlug, LegalDoc>>` (a missing page fails typecheck). All are **drafts for legal review**.

### Admin and mobile (to build)
- Add `"@unimate/i18n": "^0.0.0"` to the app, wrap the root in `<I18nProvider locale={locale}>`.
- Admin (Next): copy the web pattern (cookie + `getT` + `LocaleSync`). Move `LocaleSync`/`persistLocale` into a shared place if admin needs the exact same code; they only depend on a Supabase browser client.
- Mobile (Expo): store the local choice in AsyncStorage/SecureStore, read the device list from `expo-localization` (`getLocales().map(l => l.languageTag)`), and call `reconcileLocale` once after the session loads, then apply the result:

```ts
const r = reconcileLocale({ profile: session ? { locale: p.locale, localeSetAt: p.locale_set_at } : null, storedLocale, deviceLocales });
if (r.shouldWriteLocal) await storage.set("um-locale", r.effective);
if (r.shouldWriteProfile) await supabase.from("profiles").update({ locale: r.effective }).eq("id", uid);
setLocale(r.effective);
```
- Explicit changes: `const plan = changeLocale(next, signedIn)` then write what the plan says. Update `auth.updateUser({ data: { locale } })` too (emails).
- Server-side (edge functions, email senders): `renderNotification` (below).

## Sync rules (source of truth)

Implemented as pure functions in `packages/i18n/src/resolve.ts`, table-tested in `resolve.test.ts`.

1. `resolveLocale({ profileLocale, storedLocale, deviceLocales })`: profile (authenticated only) > stored > first supported device locale > **az**. Device tags map by primary subtag: `ru-RU` -> ru, `tr-TR` -> tr, `az-Latn-AZ` -> az; unknown -> az.
2. Signed out: stored choice, else device, else az. Nothing is written.
3. First authenticated load (`reconcileLocale`):
   - `profiles.locale_set_at` set: **the profile wins**; the local copy is refreshed (cross-device sync).
   - `locale_set_at` null (never chosen): the local/device choice is **pushed** to the profile (only when a real stored/device choice exists; a bare az default is not turned into a "choice").
4. Changes while signed in write both (`changeLocale`); while signed out, only local.
5. `locale_set_at` is stamped by the database trigger `profiles_stamp_locale_set_at` (migration `20260101003900`) whenever `locale` is in an UPDATE's SET list. The client never sends it.
6. Limit: a user who never chose a language and is still on the default az (null timestamp) will have az replaced once by the device language at their first load after this migration. Rows with a non-az locale were backfilled as "chosen".

## Notifications and emails

### `renderNotification(template, params, locale, { escape })`
Mirrors `public.render_notification_fields`: requested locale -> az -> legacy title/body -> the key. Uses core `renderEmailTemplate`
rules: substituted values are HTML-escaped by default (single pass, template text trusted). Pass `{ escape: false }` for React/RN text and push
payloads. `groupTemplates(rows)` turns `notification_templates` rows into templates. Templates use simple `{key}` placeholders (no ICU) because the SQL side substitutes the same way.

### Supabase auth emails
Files: `supabase/templates/{confirm,recovery,magic_link,invite,email_change}_{az,tr,en,ru}.html` (20). Table-based, 560 px max, inline
styles, logo `{{ .SiteURL }}/brand/full-logo.png` (served by the web app from `apps/web/public/brand`). Each file's header comment holds the
subject line and a "native-speaker review needed" notice. Variables used: `.SiteURL`, `.ConfirmationURL`, `.Email`, `.NewEmail`. `email_change` is sent for the new address.

How Supabase actually supports this (from the Supabase docs as I know them; **not verified against a live project**):
- Hosted Supabase / the CLI accept **one template per email type** (dashboard, or `[auth.email.template.<type>]` with `subject` and `content_path` in `config.toml`). There is no per-language template slot.
- Templates are Go templates and can read user metadata via `.Data` (`user_metadata`), so one template can branch on `.Data.locale`.
- The **Send Email Auth Hook** (HTTPS or Postgres function) receives the user (including `user_metadata`) and `email_data` (`token`, `token_hash`, `redirect_to`, `site_url`, `email_action_type`) and sends the mail itself, which allows any per-locale template and subject.

Pick one:
- **A. Conditional template (no extra service).** Run `node scripts/build-auth-templates.mjs`. It writes `supabase/templates/combined/<type>.html`, one document per type that renders tr/en/ru by `.Data.locale` and **az otherwise**. Wire them, for example:
  ```toml
  # supabase/config.toml (not committed: unverified)
  [auth.email.template.confirmation]
  subject = "UNIMATE"
  content_path = "./supabase/templates/combined/confirm.html"
  # recovery -> recovery.html, magic_link -> magic_link.html, invite -> invite.html, email_change -> email_change.html
  ```
  Limitation: the **subject** is one string per type. Use a neutral subject (e.g. "UNIMATE") unless your Supabase version templates the subject too (unverified).
- **B. Send Email Auth Hook (recommended if per-language subjects matter).** An edge function reads `user.user_metadata.locale`, picks `<type>_<locale>.html`, replaces `{{ .SiteURL }}`, `{{ .ConfirmationURL }}` (built from `site_url`, `token_hash`, `redirect_to`), `{{ .Email }}`, `{{ .NewEmail }}`, takes the subject from the file's header comment, and sends through the mail provider. Not written here: no provider and no hosted project exist yet.

Both options depend on `user_metadata.locale`, which the web app writes at sign-up (`options.data.locale`, from the cookie language) and on every change (`persistLocale`). Sign-up emails use the language chosen before signing up; later emails follow the profile.

Not verified: that `.Data` is populated for each email type (invite and email_change in particular); how `{{ if and ... }}` behaves when `.Data.locale` is absent on the deployed GoTrue version; the `config.toml` keys and `content_path` base directory of your CLI version; that email clients render the logo (it must be reachable at the public `SiteURL`).

## Adding a key
1. Add it to `packages/i18n/src/messages/en.ts` (English defines `Messages`; the key becomes a typed `MessageKey`).
2. Add it to `az.ts`, `tr.ts`, `ru.ts` (each `satisfies Messages`: a missing key fails typecheck). Hand-write the translation; do not machine-translate.
3. Use plurals where a number sits next to a noun; Russian needs `one/few/many` only when the noun form changes (`other` is required).
4. `npx vitest run packages/i18n apps/web/src/i18n` checks key parity, placeholder parity and the hardcoded-string scan.

## Adding a language
1. Add the code to `LOCALES`, `LOCALE_NAMES` (endonym), `bcp47` (`locales.ts`), the `catalogs` map (`catalogs.ts`) and a `messages/<code>.ts`.
2. Add `<code>` to the DB checks (`profiles_locale_check`, `notification_templates.locale`, `system_content.locale`) in a **new** migration, and seed all notification templates.
3. Add legal pages (`content/legal/<code>.ts`, typed record fails until present), 5 email templates, and extend `BRANCHES`/the `else` chain in `scripts/build-auth-templates.mjs`.
4. Check `Intl` plural rules and collation for the language and add tests like `message.test.ts` / `collate.test.ts`.
